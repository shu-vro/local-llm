You are a senior React Native mobile engineer and local-first AI architect. Build a complete offline-first mobile app that works like a local ChatGPT clone using Cactus Compute for on-device inference.

Project goal:
Create a production-quality React Native app that provides a ChatGPT-like mobile chat experience, runs the AI model locally through Cactus Compute, stores all data locally in SQLite, supports multiple chat threads, supports file attachments where technically possible, and does not depend on any external runtime service after the one-time model download.

4. No cloud fallback. Explicitly disable or avoid any cloud routing.
5. No external API calls except the one-time model download.

Create a CactusProvider that:

Generation behavior:

- When the user sends a message:
  1. Create user message in SQLite.
  2. Create assistant placeholder message with status='streaming'.
  3. Build the Cactus message array from recent thread history.
  4. Include a system message that says:
     “You are a private local AI assistant running fully on this device. Be helpful, concise, and honest. If a file or modality is unsupported, say so clearly. Do not claim to have internet access. Do not claim to have uploaded or downloaded anything except the local model if asked.”
  5. Stream tokens into the assistant message.
  6. Persist incremental content safely.
  7. Mark assistant message complete.
  8. Update thread updated_at and title.
- If this is the first user message in a thread, generate a short local title from the first message using either:
  - a cheap prompt to the local model, or
  - a deterministic fallback from the first 4–8 words.
- Support stop/cancel during streaming.
- Support retry/regenerate.

Prompt building:

- Keep the last N messages within a configurable token/message budget.
- Prefer recent messages.
- Include attachment summaries when available.
- For unsupported attachments, include a note in the message context:
  “[Attachment stored locally but not processed: filename, mime type].”

Attachment behavior:

- Images:
  - If Cactus completion supports images for the chosen model, pass image paths in the message payload.
  - Otherwise store and preview only, then tell the user image understanding is unavailable.
- Audio:
  - If Cactus supports audio completion with Gemma 4 E2B, pass raw PCM/audio as required by the API.
  - Otherwise store only.
- Video:
  - Do not attempt remote processing.
  - If direct local video input is unsupported, store only and display unsupported message.
- PDF/document:
  - Store locally.
  - If native text extraction is implemented, extract text, chunk it, store extracted_text, and make it available to RAG/context.
  - If not implemented, show a graceful unsupported state.
- Never crash because of an unsupported file type.
